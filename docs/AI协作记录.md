## 2. 提示词与交互实录

用户同时粘贴了课程实验要求全文（选题方式、提交清单、六项评分标准），随后给出自己的选题描述，原文如下：

> 这是我的作业要求，需要生成一个需求文档，我选择做的应用是一个网页2D横版平台跳跃游戏，游戏可以实现正常的左右移动、跳跃，有敌人，有武器系统、背包系统、不同关卡场景，有技能数，金币系统、hp和sp，大致这样，你帮我实现一份需求文档

## 3. AI 自主探索记录（撰写前的事实收集）

AI 在提出澄清问题之前先对仓库做了非破坏性探查，这些结果直接构成需求文档 2.2 节"现状基线"：

| 探查动作 | 得到的事实 | 对需求的影响 |
|---|---|---|
| 读取 `package.json`、`tsconfig.json`、`.editorconfig` | phaser 4.0.0、vue 3.5.13、vite 6.3.2、typescript 5.7.3；`strict: true`；4 空格缩进、UTF-8、CRLF | 约束 C1、C5；NFR-08 |
| 读取 `src/game/main.ts` | 画布 1024×768，`type: AUTO`，**未配置 `physics` 字段** | FR-01 必须新增 Arcade Physics 配置 |
| 读取五个场景文件与 `EventBus.ts` | 仅有空壳场景与 Logo 漂浮动画；已存在 Phaser 与 Vue 之间的事件总线 | FR-15 可复用骨架；DR-04 以此为基础设施 |
| 读取 `log.js` | `dev` 与 `build` 脚本会向 `gryzor.co` 发送一次构建期 GET 请求 | **关键发现**：NFR-09 的"零网络请求"必须限定为浏览器运行时，否则该需求与仓库现状直接矛盾 |
| 检查 `node_modules/phaser/dist` 与类型定义 | `phaser-arcade-physics.js` 存在；`tilemapTiledJSON` 有 7 处引用；`Scale.FIT` 存在；随包提供 `physics-arcade`、`tilemaps` 等 skills 文档 | 证明 FR-01、FR-11、NFR-06 技术可行 |
| 检查 `package.json` 脚本与 devDependencies | 无测试框架、无 ESLint 配置 | NFR-08 的覆盖率指标必须显式声明依赖 D2（新增 Vitest） |
| 网络检索素材许可 | Kenney 全站资源为 CC0；Pixel Frog《Pixel Adventure 1》为 CC0；Ansimuz《SunnyLand Woods》为 CC0；**Pixel Frog《Tiny Swords》为自定义许可而非 CC0** | 约束 C4 增加"逐包核实、不可按作者一概而论"的强制要求 |

### 5.2 撰写阶段由撰写者复核后的修订

以下修改发生在文档撰写过程中，由撰写者对 AI 草案做技术复核后裁定，是"未直接照搬 AI 原始输出"的具体体现：

| 编号 | AI 草案值 | 修订后 | 修订理由 |
|---|---|---|---|
| MR-01 | 受击无敌帧 1.2 s | 0.8 s | 1.2 s 在密集敌群中让玩家近乎无敌，削弱战斗张力；0.8 s 约等于一次攻击硬直加一次位移的时间 |
| MR-02 | 武器升级成本 `round(60 × n^2)` | `round(60 × n^1.5)` | 平方增长下 1→5 级累计需 1800 金币（60+240+540+960），已超过单场景全部金币产出（1230~1880），满级武器在通关前不可达；改为 n^1.5 后累计 1022 金币，约占单场景产出的 55%~83% |
| MR-03 | 跳跃初速度 430 px/s、重力 1200 px/s²（跳高约 77 px ≈ 2.4 瓦片） | 480 px/s、1300 px/s²（跳高约 88 px ≈ 2.8 瓦片） | 角色碰撞体高 44 px（约 1.4 瓦片），2.4 瓦片跳高不足以稳定跨越 3 瓦片高差，需留操作余量 |
| MR-04 | 技能点来源于角色经验值升级体系 | 改为关卡内收集回响碎片（每关 3 枚）+ Boss 奖励 | 删除一整套经验曲线与等级 UI，用可数收集物替代，降低实现与验收成本 |
| MR-05 | 技能树点数恰好够全解锁 | 全解锁需 46 SKP，玩家最多获得 42 SKP | 刻意制造 build 取舍，避免全解锁让技能树失去决策价值 |
| MR-06 | 敌人数量未设上限 | 同屏敌人上限 24，超出则冻结最远敌人 AI | 为 NFR-01 帧率指标留出确定性上界 |
| MR-07 | 即死区按持续扣血直至死亡处理 | 接触即死区立即死亡，不扣 HP | 深渊坠落过程中持续掉血在视觉上不合理，且会与 i-frame 规则冲突 |
| MR-08 | 关卡内小地图作为 HUD 组成部分 | 移入 8.2 范围外 | 线性横向关卡中小地图信息价值低，且增加每帧绘制开销 |

## 6. 否决清单（AI 提出但被否决）

| 编号 | AI 提出的内容 | 否决者 | 否决理由 |
|---|---|---|---|
| RJ-01 | 完整账号系统（注册登录、云存档、跨设备同步） | 用户（R2） | 需服务端与鉴权，远超个人课程工期；与"打开即玩"定位冲突 |
| RJ-02 | 在线排行榜与分数上报接口 | 用户（R2） | 无服务端；离线环境无法防作弊，排名不可信 |
| RJ-03 | 手柄支持与热插拔 | 用户（R3） | 需引入输入抽象层，收益低于工期成本；已核实 Phaser 具备 gamepad 能力，保留为未来可恢复路径 |
| RJ-04 | 移动端触屏适配 | 用户（R3） | 会改变操作手感基准，导致 NFR-02 输入延迟指标需重新定义 |
| RJ-05 | SP 与耐力双资源体系 | 用户（R3） | 两条资源的制约规则难以无二义地表达，HUD 与教学成本翻倍 |
| RJ-06 | 无尽模式与随机关卡生成 | 用户（R3） | 随机关卡无法定义确定的验收标准，与可验证性维度冲突 |
| RJ-07 | 外观解锁（皮肤、特效） | 用户（R5） | 需额外美术资源，对核心玩法无贡献 |
| RJ-08 | 单命硬核模式 | 用户（R4） | 与 U1 休闲玩家失败惩罚轻的诉求直接冲突 |
| RJ-09 | 轻量叙述式文档（不强制编号） | 用户（R4） | 会削弱追溯性与可验证性，而这两项合计占 30 分 |
| RJ-10 | 角色经验值与等级体系 | 撰写者（见 MR-04） | 额外一整套数值曲线与 UI，工期不允许 |
| RJ-11 | 引入 Matter.js 刚体物理 | 撰写者 | 平台跳跃用 AABB 与斜面校正即可，刚体会带来不可控的旋转与摩擦行为，调试成本高（记为约束 C3） |
| RJ-12 | 面向玩家的关卡编辑器 | 撰写者 | 属于独立产品级功能，与"提供完整可玩内容"的核心目标无关 |
